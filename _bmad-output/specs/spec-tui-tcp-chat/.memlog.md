- (decision) Slug chosen as 'tui-tcp-chat' rather than 'ai-training-go' — the brief covers both the monorepo and the first app; this spec targets the concrete buildable thing (the chat app), monorepo-wide conventions live in a conventions.md companion
- (capability) CAP-1 intent: server can accept multiple concurrent TCP client connections and broadcast text messages among them. success: 2+ clients connected simultaneously; a message sent from one client is received by all others.
- (capability) CAP-2 intent: user can run a Bubble Tea TUI client that connects to the chat server over TCP and exchanges messages live. success: launching the client connects to the server; messages typed locally appear on other connected clients, and incoming messages render in this client's TUI without manual refresh.
- (capability) CAP-3 intent: user can set a username that tags every message they send, visible to other clients. success: each message rendered in any client's TUI shows the sender's username alongside the text.
- (capability) CAP-4 intent: developer can start and rebuild the chat server via Docker Compose from the repo root. success: 'docker compose up' and 'docker compose up --build tui_tcp_chat' from repo root bring up the service with no manual steps outside Docker.
- (constraint) Server concurrency model is goroutine-per-connection plus a single broadcaster goroutine coordinating via channels, no mutex — explicit stated learning goal from the brief (Why: goroutines/channels), not left open to implementer choice
- (constraint) TCP networking uses Go's standard 'net' package directly, no higher-level framework/library abstraction — explicit stated learning goal from the brief (Why: net package)
- (constraint) TUI must be built with Bubble Tea (Charm ecosystem) — chosen in the brief, not open for substitution
- (constraint) Lives at apps/tui_tcp_chat/ inside the ai-training-go monorepo and uses its single root go.mod (not a per-app module) — see conventions.md companion for the full monorepo convention
- (non-goal) No chat rooms in v1 — single shared channel only
- (non-goal) No message history or persistence — messages only exist live in the session
- (non-goal) No authentication, TLS, or encryption — plain TCP, username is a display label only, not identity
- (non-goal) No reconnect/resilience handling — a dropped connection just ends that client's session
- (note) Success signal: v1 is done when 2+ Bubble Tea TUI clients connect to the Go TCP server, exchange text messages tagged with usernames, and the whole thing starts via 'docker compose up' from the repo root — no manual steps outside Docker
- (assumption) Assumed Go and Docker toolchain setup on the developer's machine is a prerequisite to executing this spec, not itself a spec capability — brief notes neither is installed yet
- (question) Brief specifies 'docker compose up' as the run command but doesn't address how an interactive Bubble Tea TUI client attaches its terminal through Compose (plain 'up' multiplexes non-interactive service logs by default). Needs a human decision: does the client run via 'docker compose run' per session, via 'tty: true'/'stdin_open: true' plus 'attach', or outside Docker on the host connecting to a dockerized server?
